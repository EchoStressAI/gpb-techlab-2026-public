# Объяснимость результатов

## 1. Цель

Объяснимость нужна не для того, чтобы превратить score в психологический диагноз, а чтобы пользователь понимал:

- что именно было проанализировано;
- достаточно ли данных;
- какие категории факторов поддержали результат;
- какие ограничения действуют;
- что делать с результатом дальше.

## 2. Минимальный explainability contract

Хороший runtime-ответ должен позволять восстановить:

```text
model_id
case_id
analysis_horizon
quality_status
score/status
supporting factors
warnings / limitations
```

## 3. Разделение результата и качества

Рекомендуется не смешивать score и качество входа в одно число.

Пример:

```json
{
  "status": "ok",
  "score": 0.71,
  "quality_status": "LIMITED_EVIDENCE",
  "warnings": ["low_speech_coverage"]
}
```

В таком случае интерфейс может показать, что численный signal рассчитан, но его интерпретация ограничена.

## 4. Типы факторов

Публичный слой может отображать факторы на безопасном уровне абстракции:

- речевое покрытие;
- динамика пауз/темпа;
- акустическая стабильность;
- prosodic/emotional representation;
- текстовый/диалоговый сигнал, если он используется runtime;
- конфликт или согласованность нескольких сигналов.

Точные proprietary формулы, коэффициенты и внутренние universal fusion rules публиковать не требуется.

## 5. Нельзя читать технические классы буквально

Если внутренняя модель использует классы вроде `Scared`, `Sad`, `Angry`, это названия технических классов representation.

Неверно:

> «Модель доказала, что сотрудник испуган».

Корректнее:

> «Во внутреннем эмоциональном representation выросла компонента, ассоциированная с классом X; это один из факторов score и требует интерпретации вместе с другими сигналами и quality».

## 6. CASE 1

Для CASE 1 explanation должен прежде всего отвечать:

- сколько клиентского материала было доступно в первые 60 сек;
- прошёл ли evidence/quality gate;
- какой тип сигнала повысил/понизил риск;
- есть ли основания для дополнительной проверки.

Explanation не должен утверждать, что мошенничество установлено.

## 7. CASE 2

Для CASE 2 explanation должен прежде всего разделять:

- эмоциональную реакцию;
- возможный сигнал утомления/истощения;
- качество и объём речи;
- ситуативный контекст;
- ограничения индивидуального переноса.

Единичный score не должен использоваться как автоматическая характеристика личности или профессиональной пригодности.

## 8. Временная честность

Если runtime анализирует 0–180 сек, объяснение не должно ссылаться на эпизод после 180 сек как на причину score.

Это особенно важно при ручной рецензии длинных звонков.

## 9. Provenance

При возможности runtime должен сохранять безопасный provenance:

- версия модели;
- версия preprocessing;
- фактическое аналитическое окно;
- количество валидных сегментов;
- признаки fallback-режима;
- статус достаточности данных.

Публичный ответ не обязан раскрывать файловые пути, закрытые SHA/model inventory или внутренние research identifiers.

## 10. Рекомендации для UI

Рекомендуемый порядок отображения:

1. итоговый статус;
2. quality badge;
3. короткое объяснение факторов;
4. предупреждения;
5. технические детали по запросу пользователя.

Цветовой индикатор без текста недостаточен: пользователь должен видеть, **почему** система считает результат уверенным или ограниченным.
