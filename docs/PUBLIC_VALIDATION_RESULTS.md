# Public Validation Results · GPB TechLab 2026

Этот документ собирает **публично безопасные aggregate validation results** финальных конкурсных контуров CASE 1 и CASE 2.

Цель документа — дать жюри и техническому reviewer конкретные числа, не смешивая:

```text
внутреннюю model validation
≠
CONTROL без известных labels
≠
будущую скрытую/внешнюю проверку Банка
≠
CI public repository
```

Здесь не публикуются row-level predictions, идентификаторы сотрудников/звонков, model weights, exact coefficients, внутренние thresholds, feature tables, формула тревожности или универсальная интегральная методология EchoStressAI.

---

## 1. Критерии заказчика

По техническому заданию:

### CASE 1

Основная метрика — **PR AUC** как метрика несбалансированной бинарной классификации. Дополнительно используется ROC AUC; в ТЗ указан ориентир **75%**. Банк также допускает каскадную схему, где часть уверенно безопасных случаев исключается на первом уровне, а неоднозначные случаи направляются на дополнительную проверку.

### CASE 2

Целевой критерий — **ROC AUC ≥ 0.75**. Отдельный критерий касается понятности/доступности объяснений пользователю.

Важно: критерии ТЗ и результаты конкретной model version — разные сущности. Ниже приведены именно validation results текущих конкурсных PRIMARY-контуров.

---

# CASE 1 · возможное внешнее воздействие на клиента

## 2. Public PRIMARY scope

Публичный основной контур CASE 1 построен так, чтобы итоговый model signal относился именно к клиенту.

Для основной версии:

- анализируется клиентская сторона;
- рабочее окно — первые **60 секунд**;
- речь оператора не входит в PRIMARY model input;
- CONTROL labels не используются для обучения или выбора модели;
- pseudo-labeling/transductive перенос через CONTROL не используется;
- score является ранговым model signal, а не вероятностью воздействия.

Причина такого ограничения принципиальна: в ходе исследования был обнаружен очень сильный операторский сигнал, однако отдельный аудит показал, что значительная его часть связана с банковским workflow/процедурой. Поэтому этот результат не был выдан за чистый сигнал состояния клиента.

## 3. Данные CASE 1

На момент финального конкурсного validation snapshot:

| Набор | Всего | Target | Non-target |
|---|---:|---:|---:|
| Размеченные звонки | 300 | 45 | 255 |
| Train | 210 | 31 | 179 |
| Validation | 45 | 7 | 38 |
| Test | 45 | 7 | 38 |

Всего в исходной банковской выгрузке — **360 двухканальных звонков**.

Для отдельного CONTROL60 labels при построении/выборе основной модели не использовались и в публичном validation claim не подменяются предположениями.

## 4. Основные результаты CASE 1

Public PRIMARY / CLIENT-only validation:

| Метрика | Результат |
|---|---:|
| PR AUC | **0.365** |
| ROC AUC | **0.757** |
| Weighted F1 | **0.819** |

ROC AUC текущего clean CLIENT-only контура находится выше указанного в ТЗ ориентира 0.75 по дополнительной метрике.

PR AUC остаётся основной метрикой задачи из-за дисбаланса классов и поэтому публикуется отдельно, а не заменяется более удобной ROC AUC.

## 5. Safe-negative cascade

Отдельно проверялся первый каскадный уровень — зона, в которой система может с высокой уверенностью выделить часть случаев с низким сигналом и не отправлять их сразу в более дорогой/сложный анализ.

Зафиксированные aggregate результаты:

| Показатель | Результат |
|---|---:|
| Precision класса `not influenced` в safe-negative зоне | **1.00 median** |
| Coverage | **≈17.8%** |
| Worst positive retention | **≈97.8%** |

Это не означает, что 17.8% всех звонков «гарантированно безопасны». Это operating-region result конкретной validation procedure и его следует читать вместе с ограничениями выборки.

## 6. Insufficient evidence

Система отдельно проверяет достаточность клиентской речи и не превращает недостаток информации в «низкий риск».

В размеченном exact-60 наборе недостаточно данных было для **22 из 209** звонков; среди них были и target cases. Поэтому `INSUFFICIENT_EVIDENCE` является отдельным содержательным outcome, а не технической ошибкой.

## 7. Что мы намеренно не заявляем по CASE 1

Нельзя интерпретировать опубликованные числа как:

- вероятность воздействия в процентах;
- доказательство факта мошенничества;
- результат на CONTROL с неизвестными labels;
- доказательство полного отсутствия workflow confounding во всех возможных данных;
- внешнюю независимую банковскую validation.

Корректная формулировка: текущая CLIENT-only версия даёт ранговый сигнал по клиенту, имеет отдельный evidence gate и прошла внутреннюю конкурсную validation по зафиксированному protocol; следующий сильный шаг — скрытая/внешняя проверка на новых данных Банка.

# CASE 2 · риск неблагоприятного профессионального состояния

## 8. Public PRIMARY scope

CASE 2 оценивается не как диагноз по одному звонку, а на уровне **employee-period**.

Рабочая постановка:

- по каждому звонку используется раннее окно до **180 секунд**;
- анализируется сторона сотрудника;
- один звонок даёт предварительный acoustic signal;
- серия наблюдений формирует относительный risk signal за период;
- результат не является calibrated probability и не является медицинским/кадровым диагнозом.

Финальная конкурсная PRIMARY-ветка выбрана как акустическая: более сложное объединение с текстовым контуром давало лишь небольшой прирост, поэтому для serving был выбран более простой и устойчивый вариант.

## 9. Данные CASE 2

На финальном snapshot:

- **158** банковских звонков;
- **98** — обучающая часть;
- **60** — CONTROL;
- **11** сотрудников в обучающей части;
- **4** сотрудника в CONTROL;
- **25** employee-period наблюдений в основном validation protocol.

CONTROL не использовался для выбора финальной модели.

## 10. Основные результаты CASE 2

Текущий внутренний конкурсный validation result:

| Метрика | Результат |
|---|---:|
| Period ROC AUC | **0.870** |
| Period PR AUC | **0.806** |
| Operator-equal ROC AUC | **0.882** |

Основной ROC AUC текущего validation snapshot превышает целевой ориентир ТЗ **0.75**.

Operator-equal metric приведена отдельно, чтобы pooled result не скрывал дисбаланс вклада отдельных сотрудников.

## 11. Что особенно важно в CASE 2

### Employee-held-out logic

Validation организуется так, чтобы переносимость между сотрудниками оценивалась отдельно от способности модели запоминать индивидуальный голос.

### Relative score, not diagnosis

`risk_score` — относительный model signal. Его нельзя подписывать как «вероятность выгорания X%».

### Один звонок не равен периоду

Один файл может дать акустический signal, но целевой construct устойчивого профессионального состояния интерпретируется на серии наблюдений.

### Supporting state отдельно

Утомление, дистресс и эмоциональный фон могут быть полезными дополнительными сигналами, однако они не подменяют PRIMARY burnout-related risk и не смешиваются с ним без отдельного доказанного прироста.

## 12. Explainability criterion

ТЗ отдельно требует прозрачности и доступности объяснений.

Текущая архитектура предоставляет техническую объяснимость и quality/evidence semantics, однако **этот документ не заявляет, что human acceptance ≥80% уже измерен**, пока нет отдельного зафиксированного пользовательского protocol/report.

Это принципиально: наличие XAI в интерфейсе и формально измеренная понятность для пользователей — разные виды evidence.

## 13. Ограничения CASE 2

Публичные метрики выше являются текущим исследовательским validation result конкурсной версии. Они не должны описываться как завершённая внешняя клиническая или независимая банковская validation.

Следующие шаги:

- скрытая/внешняя проверка на новых данных;
- аудит сопоставимости шкал/labels;
- отдельная human-XAI acceptance проверка;
- проверка устойчивости на новых сотрудниках и периодах;
- дальнейшая оценка within-person dynamics.

# 14. Что эти числа доказывают — и чего не доказывают

| Claim | Что поддерживает | Чего не доказывает |
|---|---|---|
| CASE 1 ROC AUC 0.757 | внутреннюю discriminative validation CLIENT-only модели | вероятность воздействия, качество на неизвестном CONTROL |
| CASE 1 PR AUC 0.365 | ranking quality при дисбалансе на зафиксированном protocol | достижение любой произвольно выбранной business threshold |
| Safe-negative precision 1.00 median | наличие полезной высокоточной зоны в validation | абсолютную гарантию безопасности нового звонка |
| CASE 2 Period ROC AUC 0.870 | внутреннюю employee-period validation | медицинскую диагностику или внешнюю validation |
| CASE 2 PR AUC 0.806 | ranking quality на текущем period protocol | калиброванную вероятность выгорания |
| Operator-equal ROC AUC 0.882 | устойчивость aggregate ranking при выравнивании вклада сотрудников | полноценную within-person longitudinal validation |

## 15. Versioning rule

Эти результаты относятся к финальному конкурсному validation snapshot сентября 2026 года. Перед release/demo их следует связать с конкретными `model_id`, runtime build и public repository commit/tag.

Если модель, preprocessing или validation protocol меняются, метрики должны пересчитываться и публиковаться как новый version-specific result.

Связанные документы:

- `VALIDATION_PROTOCOL.md` — правила validation;
- `VALIDATION_EVIDENCE_INDEX.md` — типы evidence;
- `CASE1_MODEL_CARD.md` / `CASE2_MODEL_CARD.md` — scope и ограничения;
- `LIMITATIONS_AND_RESPONSIBLE_USE.md` — правила интерпретации;
- `PUBLIC_RELEASE_VERSIONING.md` — release identity.
