# Демонстрационный сценарий

## 1. Цель демонстрации

Показать не отдельный график или score, а полный рабочий путь:

```text
загрузка звонка
→ выбор кейса
→ анализ фиксированного окна
→ модельный результат
→ quality
→ объяснение
→ корректная продуктовая интерпретация
```

## 2. Подготовка

Перед демонстрацией проверить:

```bash
curl -fsS http://127.0.0.1:8080/health
curl -fsS http://127.0.0.1:8080/api/v1/readiness
```

Readiness должен быть `200`.

Также заранее проверить 2–3 demo-файла без персональных данных и убедиться, что интерфейс корректно показывает:

- CASE 1;
- CASE 2;
- normal/limited evidence;
- runtime unavailable/error state.

## 3. Сценарий CASE 1

### Шаг 1. Загрузка

Выбрать `CASE_1` и загрузить аудиозапись.

### Шаг 2. Объяснить окно

Сказать:

> «Для первого кейса система ограничивает анализ первыми 60 секундами, чтобы ранняя оценка не использовала последующий разговор».

### Шаг 3. Показать результат

На экране должны быть:

- итоговый risk/status;
- достаточность материала;
- model id/version;
- supporting explanation;
- предупреждение, если данных недостаточно.

### Шаг 4. Правильно интерпретировать

Сказать:

> «Это дополнительный антифрод-сигнал. Он не устанавливает факт мошенничества сам по себе и должен использоваться вместе с банковским процессом проверки».

## 4. Сценарий CASE 2

### Шаг 1. Загрузка

Выбрать `CASE_2` и загрузить аудиозапись.

### Шаг 2. Объяснить окно

> «Второй кейс использует первые 180 секунд релевантной речи сотрудника. Мы отдельно показываем качество входа, потому что три минуты записи не означают три минуты речи».

### Шаг 3. Показать результат

Показать:

- score/state signal;
- quality badge;
- фактическое речевое покрытие, если его отдаёт runtime;
- explanation;
- ограничения.

### Шаг 4. Правильно интерпретировать

> «Это исследовательский/операционный сигнал состояния, а не диагноз и не основание для автоматического решения о сотруднике».

## 5. Что особенно хорошо показать комиссии

1. **Fail-closed behavior** — отключить/смоделировать недоступность runtime и показать, что API не придумывает число.
2. **Readiness** — продемонстрировать, что система различает «API жив» и «модели готовы».
3. **60/180 sec contract** — это важная часть воспроизводимости.
4. **Quality layer** — сильный score при плохом входе не выдаётся как безусловно надёжный результат.
5. **Explainability** — пользователь получает основания и ограничения, а не только цвет светофора.
6. **On-prem topology** — аудио может оставаться внутри локального контура.

## 6. Нежелательные формулировки

Не использовать на защите:

- «модель точно определяет выгорание»;
- «мы знаем, что клиент под влиянием мошенника»;
- «эмоция Scared означает страх»;
- «если score высокий, сотрудник плохо работает»;
- «любой звонок за 180 секунд содержит достаточно речи».

## 7. Предпочтительные формулировки

Использовать:

- «дополнительный сигнал риска»;
- «модельный state signal»;
- «quality-controlled result»;
- «фиксированное временное окно»;
- «объяснение факторов»;
- «human-in-the-loop»;
- «on-prem ready integration architecture».

## 8. Demo fallback

Если live runtime неожиданно недоступен:

1. не переключаться на фиктивный score;
2. показать `/readiness`;
3. объяснить fail-closed architecture;
4. использовать заранее сохранённый **скриншот/recorded demo**, явно обозначив его как запись предыдущего успешного прогона;
5. не выдавать prerecorded result за текущий inference.

## 9. Короткий устный сценарий

> «Мы загружаем обычный звонок. Сервис маршрутизирует его в нужный кейс и физически ограничивает анализ первыми 60 или 180 секундами. Model runtime возвращает не только score, но и quality и объяснение. Если модель недоступна или данных недостаточно, интерфейс показывает это явно и не подставляет выдуманный результат. Такая архитектура позволяет развернуть весь inference локально и независимо обновлять модели без изменения публичного API».
