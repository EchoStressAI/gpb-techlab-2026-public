# Model Card · CASE 1 — риск внешнего психологического воздействия

## 1. Назначение

CASE 1 формирует дополнительный сигнал риска того, что клиент может находиться под внешним психологическим воздействием во время разговора.

Система не определяет личность мошенника и не утверждает факт мошенничества. Она помогает выделить звонки, требующие дополнительного внимания в антифрод-процессе.

## 2. Аналитический горизонт

**Первые 60 секунд** релевантной клиентской речи.

Ограничение 60 секунд является частью контракта. Последующий разговор не должен протекать в раннюю оценку и создавать временную утечку.

## 3. Анализируемая роль

Основной объект анализа — **CLIENT**.

Данные оператора могут использоваться для технического построения диалога, но не должны автоматически становиться модельным сигналом клиента.

## 4. Какие типы информации использует CASE 1

На смысловом уровне CASE 1 опирается не на один «магический признак», а на сочетание нескольких типов информации:

- **семантика клиентской речи** — содержание ответов клиента;
- **структура и содержательность ответа** — есть ли самостоятельный развёрнутый ответ или только минимальная реакция;
- **речевое/эмоциональное состояние** как supporting signal;
- **evidence sufficiency** — достаточно ли клиентской речи в раннем окне, чтобы интерпретировать model score.

Это позволяет отличать собственно model score от качества наблюдения.

Важно: публичная документация раскрывает эти смысловые группы, но не публикует обученные vectorizers, точные признаки, коэффициенты scorer, raw промежуточные probabilities или внутреннюю формулу тревожности.

Подробнее: [MODEL_SEMANTICS.md](MODEL_SEMANTICS.md).

## 5. Вход

Минимальный вход публичного integration layer:

- аудиофайл;
- `case_id=CASE_1`;
- опциональные метаданные звонка.

Локальный runtime отвечает за case-specific preprocessing и model inference.

## 6. Высокоуровневый pipeline

```text
аудио
→ выделение клиентской стороны
→ первые 60 секунд
→ сегментация/транскрипция и речевые представления
→ семантический + supporting state signal
→ case-specific scorer
→ evidence/quality gate
→ score + decision status + recommendation
```

Эта схема отражает продуктовую семантику, но не раскрывает proprietary model implementation.

## 7. Выход

Ожидаемый semantic output runtime:

- `case_id`;
- `model_id`;
- `analysis_horizon_sec=60`;
- `status`;
- risk/primary score;
- decision/status;
- evidence/quality information;
- supporting/XAI fields;
- рекомендации по следующему шагу проверки, если они предусмотрены runtime.

Публичный gateway валидирует контракт, но не пересчитывает закрытый model score.

## 8. Интерпретация score

Score следует трактовать как **модельный ранговый сигнал риска**, а не как доказательство преступления и не как юридическую вероятность события.

Рекомендуемая продуктовая логика:

```text
модельный сигнал
   +
evidence sufficiency
   +
качество данных
   +
операционный контекст
   ↓
дополнительная проверка / рекомендация
```

## 9. Evidence / insufficient-data behavior

Если в первых 60 секундах нет достаточного клиентского материала, система должна уметь вернуть отдельный статус недостаточности данных.

Недостаточность входа не должна автоматически становиться «низким риском».

Примеры причин limited evidence:

- клиент почти не говорит;
- ответы слишком короткие/несодержательные;
- существенная часть окна занята оператором;
- есть технические ограничения аудио или ошибки разделения ролей.

## 10. Explainability

CASE 1 explanation должен отвечать на вопросы:

- достаточно ли клиентской речи попало в окно;
- какой model runtime использован;
- какие смысловые категории сигналов участвовали в анализе;
- какой supporting state signal доступен;
- есть ли ограничения качества;
- является ли результат достаточным для обычной интерпретации или требует дополнительной проверки.

Безопасные публичные факты могут включать:

- client word/turn/speech coverage;
- evidence status;
- наличие/отсутствие supporting state signal;
- итоговый decision status;
- recommended next step.

Публичная документация намеренно не содержит внутренние коэффициенты scorer, proprietary feature engineering и универсальные интегральные правила EchoStressAI.

## 11. Почему тревожность — supporting signal, а не отдельный диагноз

Эмоционально-речевой сигнал может быть полезен для раннего контекста, но неспецифичен: высокий стресс или тревожность могут возникать по многим причинам.

Поэтому supporting state signal:

- не является самостоятельным доказательством внешнего воздействия;
- не должен подменять семантическую/диалоговую информацию;
- должен сопровождаться provenance/quality;
- не раскрывает в public repo внутреннюю формулу расчёта.

## 12. Известные риски

- короткая клиентская речь;
- перекрытия говорящих;
- ошибки channel/speaker routing;
- ASR-ошибки, если textual branch используется конкретным runtime;
- domain shift на других типах звонков;
- изменение поведения клиентов после первых 60 секунд;
- возможная корреляция модельного сигнала с неспецифичным стрессом, а не только с воздействием мошенника.

## 13. Корректное использование

CASE 1 следует использовать как один из сигналов системы поддержки решений. Он не предназначен для автоматической блокировки клиента без банковских правил, проверки и допустимого процессом контроля.

## 14. Версионирование

`model_id` приходит от подключённого runtime. Публичный integration layer не должен скрывать замену модели под прежним идентификатором.
