# Explainability Acceptance Protocol · CASE 2

Техническое ТЗ задаёт отдельный критерий: **прозрачность и доступность объяснений к оценке не ниже 80%**. Этот документ определяет, как измерять этот критерий так, чтобы не подменять human acceptance наличием XAI-графика или списка feature contributions.

## 1. Что именно измеряется

Проверяется не «есть ли объяснение в JSON», а понимает ли пользователь:

1. **что означает итоговый score/status**;
2. **какие наблюдаемые речевые факторы повлияли на результат**;
3. **какие ограничения есть у конкретного результата**;
4. **что является следующим допустимым действием**;
5. **чего система не утверждает** — например, что score не является медицинским диагнозом.

## 2. Что не считается explainability acceptance

Само по себе не закрывает критерий ≥80%:

- наличие SHAP/linear contributions;
- цветовая шкала;
- красивый дашборд;
- отображение top-positive / top-negative features;
- комментарий разработчика «объяснение выглядит понятным»;
- один удачный demo-case.

Нужна отдельная проверка на людях.

## 3. Рекомендуемый состав кейсов

Набор кейсов фиксируется **до** начала опроса и должен включать разные типы результата:

- обычный/низкий относительный signal;
- повышенный relative score;
- ограниченная evidence quality;
- малый speech coverage;
- пример с несколькими конкурирующими факторами;
- пример, где explanation не должно превращаться в диагноз;
- пример с history/period context, если он входит в финальный UI.

Набор не должен отбираться после просмотра ответов пользователей.

## 4. Кто оценивает

Предпочтительные группы:

- сотрудник Банка, потенциально использующий интерфейс;
- руководитель/супервизор контактного центра;
- HR/people specialist для CASE 2;
- эксперт по психофизиологии/психологии как отдельная экспертная группа.

Если участвуют несколько ролей, результаты желательно показывать и в целом, и по ролям.

## 5. Карточка оценки одного объяснения

После просмотра одного кейса reviewer отвечает на пять вопросов.

### Q1 · Смысл результата

> Понятно ли вам, что означает итоговая оценка и что она НЕ является вероятностью/диагнозом?

Ответ: `Да / Частично / Нет`.

### Q2 · Факторы

> Понятно ли, какие типы речевых факторов связаны с повышением/понижением результата?

Ответ: `Да / Частично / Нет`.

### Q3 · Ограничения

> Видно ли из интерфейса, если материала недостаточно или качество результата ограничено?

Ответ: `Да / Частично / Нет`.

### Q4 · Следующее действие

> Понятно ли, что пользователь должен делать дальше и что решение остаётся human-in-the-loop?

Ответ: `Да / Частично / Нет`.

### Q5 · Проверка неправильной трактовки

Reviewer выбирает один вариант:

- «Это дополнительный модельный сигнал, требующий контекста»;
- «Это подтверждённый диагноз сотрудника»;
- «Это вероятность увольнения/профессиональной непригодности».

Зачёт — первый вариант.

## 6. Правило расчёта

Для Q1–Q4:

```text
Да = 1
Частично = 0.5
Нет = 0
```

Q5:

```text
корректная трактовка = 1
некорректная = 0
```

Для каждого reviewer × case считается:

```text
explanation_score = mean(Q1..Q5)
```

Карточка считается **понятой**, если:

```text
explanation_score >= 0.8
AND Q5 == 1
```

Основная acceptance metric:

```text
share_of_understood_explanations =
  understood reviewer-case pairs / all valid reviewer-case pairs
```

Критерий ТЗ считается выполненным, если:

```text
share_of_understood_explanations >= 0.80
```

## 7. Рекомендуемый размер проверки

ТЗ не задаёт sample size. Для конкурсного MVP рекомендуется не ограничиваться одним reviewer.

Практический минимальный дизайн:

```text
>= 20 distinct cases
>= 5 reviewers
>= 100 reviewer-case assessments
```

Если это невозможно, меньший sample допускается, но должен быть явно указан вместе с uncertainty/ограничением.

## 8. Дополнительные показатели

Полезно отдельно считать:

- долю правильной трактовки Q5;
- acceptance по каждой роли reviewer;
- acceptance по типам кейсов;
- acceptance для limited-evidence кейсов;
- долю случаев, где пользователь не заметил quality warning;
- median time-to-understanding;
- основные причины оценки `Частично/Нет`.

## 9. Pre-registration

До начала проверки фиксируются:

```text
UI/release commit
CASE 2 model_id
набор cases
reviewer roles
вопросы
scoring rule
acceptance threshold 0.80
exclusion rule
```

После просмотра результатов вопросы и threshold не меняются в рамках той же проверки.

## 10. Что считать invalid assessment

Оценка исключается только по заранее определённым причинам, например:

- технический сбой UI;
- reviewer не завершил карточку;
- показан не тот case/release;
- отсутствовал обязательный explanation block.

Нельзя исключать ответы только потому, что reviewer оценил объяснение низко.

## 11. Отчёт

Итоговый report должен содержать:

```text
release commit
model_id
UI version
number of cases
number and roles of reviewers
number of valid assessments
main acceptance metric
Q1..Q5 breakdown
failure examples by category
limitations
calculation date
```

Row-level персональные данные reviewer в public repo не требуются.

## 12. Public-safe publication

В public documentation можно публиковать:

- aggregate acceptance %;
- sample size;
- reviewer-role breakdown;
- wording questionnaire;
- anonymized error categories;
- release/model identity.

Не следует публиковать без отдельного разрешения:

- имена сотрудников Банка;
- реальные банковские транскрипты;
- персональные ответы reviewer, если они идентифицируемы.

## 13. Итог

Критерий ≥80% трактуется как **измеряемая понятность explanation для пользователя**, а не как техническая полнота XAI.

Такой protocol делает explainability отдельным проверяемым свойством продукта, а не декларацией разработчика.
