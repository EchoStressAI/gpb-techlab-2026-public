# FAQ · вопросы жюри и технического reviewer

## Почему model weights не лежат в public repo?

Публичный repository отвечает за проверяемый integration/frontend contract, архитектуру, поведение системы, validation methodology и публично безопасные результаты. Model artifacts могут иметь отдельные IP/licensing/data-governance ограничения и подключаются через локальный runtime.

Это не означает, что public repo — mock: при подключённом runtime он работает end-to-end; без runtime система fail-closed и не генерирует выдуманный score.

## Значит ли это, что проект не работает без закрытой модели?

Public API/frontend можно собрать, запустить и проверить отдельно. Реальный ML inference требует подключённого case runtime. Если runtime отсутствует, API честно возвращает состояние недоступности вместо synthetic результата.

## Почему не положить fake model для красивого demo?

Потому что фиктивный score создаёт ложное ощущение работоспособности. Fail-closed поведение — часть архитектуры и критерий доверия к результату.

## Что именно можно проверить по public repo?

Можно проверить:

- API/frontend code;
- routing CASE 1 / CASE 2;
- фиксированные горизонты 60/180 секунд;
- contracts и ошибки;
- readiness/fail-closed;
- Docker/integration topology;
- quality/evidence semantics;
- публичные Model Cards;
- validation protocol и aggregate results;
- scientific/expert rationale;
- CI/public-hygiene checks.

Нельзя восстановить из public Git закрытые model weights, точные coefficients, private feature tables или универсальную интегральную методологию EchoStressAI.

## Почему CASE 1 и CASE 2 не объединены в один scorer?

Это разные задачи с разными объектами анализа, временными окнами, единицами наблюдения и правилами интерпретации. Общим является integration layer, а case-specific inference разделён.

## Почему CASE 1 только 60 секунд?

Задача требует раннего сигнала. Фиксированное окно также предотвращает использование информации, появившейся позже разговора, как скрытой подсказки для раннего решения.

## Почему CASE 1 не использует речь оператора как PRIMARY, если по ней получалась очень высокая метрика?

В исследовании действительно был обнаружен сильный operator-side signal. Дополнительный аудит показал, что значительная часть этого сигнала связана с банковским workflow и противомошенническим сценарием: оператор уже реагирует на контекст звонка.

Поэтому высокая operator-only метрика не была выдана за чистое распознавание состояния клиента. Public PRIMARY ограничен клиентской стороной. Это сознательный выбор в пользу более корректного происхождения сигнала, а не попытка максимизировать цифру любой ценой.

## Какие текущие публичные результаты CASE 1?

Для CLIENT-only конкурсного validation snapshot:

```text
PR AUC       0.365
ROC AUC      0.757
Weighted F1  0.819
```

Отдельно проверялась safe-negative зона: median precision класса `not influenced` — 1.00 при coverage около 17.8%, с высоким сохранением target cases.

Эти числа — validation metrics, а не вероятность воздействия конкретного клиента.

## Почему PR AUC CASE 1 заметно ниже ROC AUC?

Положительный класс редкий, поэтому PR AUC чувствительнее к дисбалансу и качеству работы именно по редкому target class. Именно поэтому ТЗ выделяет PR AUC как основную метрику, а ROC AUC — как дополнительную.

Показывать только более красивую ROC AUC было бы методологически неправильно, поэтому обе метрики публикуются рядом.

## Значит ли ROC AUC 0.757, что задача CASE 1 «решена на 75.7%»?

Нет. ROC AUC — качество ранжирования пар положительного/отрицательного класса на validation protocol, а не доля правильно классифицированных звонков и не вероятность воздействия.

## Что происходит, если клиент почти не говорил в первые 60 секунд?

Система должна вернуть `INSUFFICIENT_EVIDENCE`/аналогичный limited-data status. Недостаток клиентской речи не превращается автоматически в «низкий риск».

## Почему CASE 2 использует 180 секунд?

Это рабочий горизонт конкурсного кейса. При этом 180 секунд файла не означают 180 секунд полезной речи сотрудника: внутри могут быть речь клиента, паузы и технические фрагменты. Поэтому speech coverage относится к quality layer.

## Почему CASE 2 оценивается по employee-period, а не как диагноз по одному звонку?

Выгорание — устойчивый многокомпонентный construct. Один звонок может дать акустический сигнал текущего состояния, но делать сильный вывод о человеке по одной записи методологически неверно.

Поэтому основной risk signal интерпретируется на уровне серии наблюдений/рабочего периода.

## Какие текущие публичные результаты CASE 2?

Для финального конкурсного employee-period validation snapshot:

```text
Period ROC AUC         0.870
Period PR AUC          0.806
Operator-equal ROC AUC 0.882
```

Это текущий внутренний конкурсный validation result. Он не объявляется завершённой внешней/скрытой банковской validation.

## Почему CASE 2 score нельзя называть «вероятностью выгорания»?

Потому что текущий output — относительный model signal/ranking index. Калиброванная вероятность требует отдельной calibration validation. Кроме того, voice signal сам по себе не является медицинским диагнозом.

## Почему в CASE 2 выбран более простой акустический контур?

В исследовании сравнивались акустическая, текстовая и объединённая постановки. Объединение давало лишь небольшой прирост относительно сильного акустического результата, но добавляло распознавание речи и сложность serving-контура.

Для основной версии был выбран более простой акустический путь как более устойчивый и прозрачный инженерный компромисс. Exact model internals в public Git не раскрываются.

## Где точные названия всех признаков и их коэффициенты?

В public repo показываются смысловые семейства факторов и safe XAI semantics, необходимые для понимания результата. Полный exact feature vector, обученные coefficients/intercept, scaler/imputer parameters и private reference distributions относятся к model IP/runtime и не являются частью публичного контракта.

Это не мешает объяснить пользователю, какие типы речевых факторов повышают/понижают relative score и насколько достаточно данных.

## А тревожность используется?

Речевое/эмоциональное состояние может использоваться как supporting signal в тех контурах, где это предусмотрено. Но тревожность не трактуется как самостоятельное доказательство воздействия или выгорания.

Внутренняя формула расчёта тревожности и её точные промежуточные outputs в public repo не публикуются.

## Почему нельзя просто объединить все сигналы в один интегральный балл?

Технически общий продукт EchoStressAI может содержать разные state/fusion механизмы, но для банковских кейсов важно не смешивать PRIMARY business target с supporting state layers без доказанного прироста на строгой validation.

Поэтому public solution разделяет основной case-specific score, quality/evidence и supporting state information.

## Если эксперт и модель не согласны, кто прав?

Однозначного ответа без независимой ground truth может не быть. Причины расхождения могут включать разные временные окна, недостаток речи, разные психологические constructs или ограничения representation.

Экспертный review используется для error analysis и construct validation, а не как автоматическая замена банковской ground truth.

## Выполнен ли критерий понятности объяснений ≥80%?

Public repo показывает техническую explainability и интерфейс объяснений, но наличие XAI само по себе не равно измеренной human acceptance.

Пока нет отдельного зафиксированного пользовательского protocol/report, корректно **не заявлять ≥80% как достигнутую измеренную величину**.

## Использовался ли CONTROL для выбора модели?

В публичной validation story CONTROL не должен использоваться для post-hoc выбора более красивой модели/порога. Если labels неизвестны, по нему нельзя заявлять AUC. Для CASE 2 финальный snapshot отдельно фиксирует, что CONTROL не использовался для выбора основной модели.

## Почему public repo продолжает меняться, если ссылка уже передана организаторам?

Ссылка ведёт на живой repository. Исправление документации, public-safety и integration code через reviewable PR — нормальный процесс.

Для финальной демонстрации/оценки следует зафиксировать конкретный commit/tag, чтобы было однозначно понятно, к какой версии относятся code, runtime и validation claims.

## Чем `/health` отличается от `/readiness`?

`/health` показывает, что integration API жив.

`/readiness` показывает, доступны ли реальные case runtime, необходимые для inference.

## Что произойдёт, если runtime вернёт неправильный horizon или нарушит contract?

Integration layer должен отклонить такой ответ как contract error, а не пытаться «додумать» результат.

## Как обновлять модель без изменения frontend?

Сохранить публичный runtime contract и заменить versioned case runtime. Содержательно новая модель должна иметь отдельную version identity/model identity, а её metrics — собственный validation report.

## Можно ли использовать внешний облачный API?

Технически HTTP contract это допускает, но для банковского on-prem сценария предпочтителен локальный runtime внутри защищённого контура, чтобы аудио и результаты не требовали внешней передачи.
