# EchoStressAI — фронтенд

Интерфейс к сервису анализа речевых записей. Реализован по контракту API
(префикс `/v1`, кейс `CASE_2` — риск профессионального выгорания).

## Подключение к боевому сервису

Фронтенд ходит только на собственный origin по пути `/api`. Адрес сервиса
задан в конфигурации прокси, а не в коде, поэтому смена домена не требует
правок исходников.

| Где | Переменная | Значение |
|---|---|---|
| nginx (прод) | `API_UPSTREAM` | `https://backend.example.com` |
| nginx (прод) | `API_HOST` | `backend.example.com` |
| Vite (`npm run dev`) | `VITE_PROXY_TARGET` | `https://backend.example.com` |

`API_HOST` отдельно от `API_UPSTREAM` нужен потому, что это имя участвует
и в TLS SNI, и в заголовке `Host`. Без него рукопожатие с входом
не состоится.

Когда появится свой домен — направить его на тот же адрес и поменять эти
три значения.

### Токен

Токен в сборку не попадает. Он вводится на странице входа и хранится
в `localStorage` браузера; действительность проверяется запросом
`GET /v1/whoami`, по ответу которого строится меню.

Если токен не должен доходить до браузера вовсе, в `nginx.conf.template`
есть закомментированная строка: прокси подставит заголовок сам. Обратная
сторона — все действия в журнале сервиса будут записаны на одного
субъекта, а доступ к стенду начнёт полностью определяться basic auth.

## Запуск

```bash
cp .env.example .env      # указать домен стенда
htpasswd -c .htpasswd operator   # создать свой файл паролей (пакет apache2-utils/httpd-tools)
docker compose up -d --build
```

Приложение: http://localhost:5556

Проверка, что связь есть:

```bash
curl -s http://localhost:5556/api/health
curl -s -H "Authorization: Bearer <токен>" http://localhost:5556/api/v1/whoami
```

Первый запрос токена не требует и отвечает на единственный вопрос: доехал
ли запрос до сервиса. Страница входа делает его сама и прямо говорит,
если дело не в токене.

## Что реализовано из контракта

| Ручка | Право | Где в интерфейсе |
|---|---|---|
| `GET /v1/whoami` | любой токен | вход, построение меню |
| `POST /v1/calls` | `calls:submit` | форма загрузки |
| `POST /v1/calls/batch` | `calls:submit` | в API-слое, в UI пока не используется |
| `GET /v1/calls/{job_id}` | `calls:read` | опрос статуса |
| `GET /v1/calls/{job_id}/result` | `calls:read` | вкладка «Результат» |
| `GET /v1/calls/{job_id}/transcript` | `transcript:read` | вкладка «Расшифровка» |
| `GET /v1/calls/{job_id}/risk` | `risk:read` + `risk:read_internal` | вкладка «Оценка риска» |
| `GET /v1/audit` | `audit:read` | раздел «Журнал» |

## Правила показа, заложенные в код

Это не оформление, а требования контракта — менять их нельзя без
согласования.

- **`null` — «не измерено», не ноль.** Все числовые значения проходят
  через `src/utils/format.ts`, который отдаёт прочерк. Подставлять 0
  нельзя: по этим числам принимают решения о людях.
- **Оценка риска не переводится в проценты.** `risk_score` показывается
  как число 0..1 рядом с порогом. При `probability_calibrated: false`
  выводится отдельное пояснение, что значение не является вероятностью.
- **Текст предупреждения берётся из `banner`.** Когда модель пройдёт
  проверку, поле придёт `null`, и предупреждение исчезнет само —
  править вёрстку не потребуется.
- **`internal_only` — пометка о применимости, не о доступе.** Доступ
  решает сервер, поэтому интерфейс не пытается по этому полю что-либо
  скрывать.
- **Вклады модели — не причины.** Формулировок «потому что» в интерфейсе
  нет, `explanation_type` показывается как есть.
- **401 и 403 разведены.** 401 сбрасывает сессию и ведёт на вход, 403
  показывает недостающее право из `required_scope` и объясняет, что
  повторный вход не поможет.
- **Два разных 403 на ручке риска.** Без `risk:read` — «оценка закрыта».
  С `risk:read`, но без `risk:read_internal` — «оценка существует, но её
  версия не допущена к показу».
- **Пробел в данных отличается от молчания.** Ход со статусом
  `EMPTY_ASR_WITH_SPEECH` показывается иначе, чем ход без речи. Выводы
  по тексту допускаются только при `semantic_text_observable: true`.
- **Интерфейс строится по правам.** Разделы, на которые права нет, не
  показываются — вместо того чтобы показывать кнопку и получать 403.

## Ограничения загрузки

Из контракта: только PCM WAV с двумя каналами, до 512 МБ. Роли каналов
передаются явно и не выводятся из номера канала; канал с ролью
`SUPPORT_OPERATOR` обязателен.

Константы — `src/constants/upload.ts`. Предел продублирован в
`client_max_body_size` в `nginx.conf.template`: менять нужно оба места.

## Список записей

Контракт не содержит ручки «все мои задания»: состояние запрашивается по
конкретному `job_id`. Поэтому список загруженных записей ведёт клиент в
`localStorage`, а статусы подтягиваются опросом. При смене браузера
список окажется пустым — это следствие контракта, а не хранения.

Если появится ручка со списком заданий, локальный список заменяется на
неё в `src/features/calls/useJobs.ts`.

## Открытые вопросы

Три из контракта, ответы нужны от владельца продукта.

1. **Источник фронтенда для CORS.** Сейчас предполагается тот же источник:
   запросы идут на относительный `/api`, nginx проксирует их на сервис.
   При таком варианте `GPB_API_CORS_ORIGINS` заполнять не нужно.
2. **Хранение токена.** Сейчас `localStorage` (`src/auth/session.ts`).
   Токен доступен из JS и уязвим к XSS. Альтернатива — сессия на стороне
   прокси; тогда модуль хранения не нужен, а клиент перестаёт слать
   заголовок `Authorization`.
3. **Прослушивание фрагментов.** Ручки для выдачи аудио в контракте нет,
   поэтому плеера в интерфейсе тоже нет.

## Что в сервисе ещё не считается

По контракту в заглушках: эмоции по голосу, тревожность, лингвистика,
кейс 1 (мошенничество). Интерфейс показывает это явно в разделе «Стадии»
как честный пробел, а не как сбой: задание при этом `done`.

Оценка выгорания считается, но помечена внутренней.
